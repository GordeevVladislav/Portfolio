# Интернет-магазин мерча: пакет аналитических артефактов

Учебно-портфолио кейс бизнес/системного аналитика. Заказчик (владелец бренда одежды и аксессуаров) прислал голосовое сообщение и 4 письма с противоречивыми требованиями. Задача: превратить хаос в пакет артефактов для команды разработки.

**Итог в одну строку:** MVP интернет-магазина мерча с самовывозом из магазина, оплатой только картой онлайн, бронированием товара на 15 минут и подарочными наклейками при заказе от 2 000 ₽.

## Что улучшено относительно исходного решения

- Противоречия сведены в таблицу с принятым решением и пометкой, что требует подтверждения заказчика.
- BPMN исправлен: списание со склада происходит после подтверждения оплаты, а не при создании заказа (иначе оплата картой ломает логику брони). Добавлены ветки «оплата не прошла» и «таймаут оплаты».
- User Stories: добавлены граничные случаи (ровно 2 000 ₽, нет наклеек на складе, гонка за последнюю единицу), а также истории администратора.
- SQL: исходный запрос оставлен, но разобраны его проблемы (`GROUP BY name` склеивает тёзок, `DATE(col)` отключает индекс). Добавлены схема v2 (позиции заказа, остатки, брони) и параметризованные запросы.
- API: убран `user_id` из тела (пользователь определяется по токену), добавлены коды `401/409/422`, различие между «нет в наличии» и «зарезервировано другим», информация о подарке.
- Добавлена рабочая эталонная реализация брони и подарка с тестом на конкурентный доступ.

## Запуск проверок

Требуется только Python 3.9+ (без внешних пакетов; тест OpenAPI использует `PyYAML`, если он установлен, иначе пропускается).

```bash
python3 -m unittest discover -s tests -v
```

## Допущения

Письма заказчика считаются более поздними и приоритетными по сравнению с голосовым сообщением. Все допущения перечислены в [анализе требований](docs/01-requirements-analysis.md) и должны быть подтверждены заказчиком до начала разработки.
